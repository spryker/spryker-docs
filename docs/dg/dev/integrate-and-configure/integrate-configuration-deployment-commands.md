This document explains how to integrate three console commands that export configuration values to a file, restore them to the database, and import values from environment variables.

| Command | Description |
| --- | --- |
| `configuration:export` | Writes the stored values of the specified settings to a file. |
| `configuration:restore` | Restores values from the configuration export file to the database. |
| `configuration:import-environment` | Imports values from the specified environment variables into the database. |

Each command is independent. Integrate only the ones your project needs, then see [Using the commands together](#using-the-commands-together) for the case they were designed for.

## Prerequisites

Before integrating the commands, install the [Configuration Management feature](/docs/dg/dev/integrate-and-configure/integrate-confguration-feature.html).

All three commands require the settings map generated by `configuration:sync`.

Update the Configuration module to version `^1.5.0` or later.

| Module | Required version |
| --- | --- |
| Configuration | `^1.5.0` |

## Register the console commands

Before integrating the commands, install the [Configuration Management feature](/docs/dg/dev/integrate-and-configure/integrate-confguration-feature.html).

All three commands require the settings map generated by `configuration:sync`.

Update the Configuration module to version `^1.5.0` or later.

Register each command you want to use in `ConsoleDependencyProvider`.

**`src/Pyz/Zed/Console/ConsoleDependencyProvider.php`**
| --- | --- |
| Configuration | `^1.5.0` |

```php
<?php

namespace Pyz\Zed\Console;

use Spryker\Zed\Configuration\Communication\Console\ExportConfigurationConsole;
use Spryker\Zed\Configuration\Communication\Console\ImportEnvironmentConfigurationConsole;
use Spryker\Zed\Configuration\Communication\Console\RestoreConfigurationConsole;

class ConsoleDependencyProvider extends SprykerConsoleDependencyProvider
{
    protected function getConsoleCommands(Container $container): array
    {
        $commands = [
            // ...
            new ExportConfigurationConsole(),
            new ImportEnvironmentConfigurationConsole(),
            new RestoreConfigurationConsole(),
        ];

        return $commands;
    }
}
```

{% info_block infoBox "Verify the command registration" %}

Run `console list configuration` and confirm that the registered commands appear in the output.

{% endinfo_block %}

## configuration:export

```bash
console configuration:export <setting key> [<setting key> ...]
```

Writes the stored value of each specified setting to a file so that you can restore the values after an operation clears the database.

The command reports settings that it skips:

- **Secret settings:** Settings declared with `secret: true` in the schema are not written to the export file.
- **Settings without stored values:** Settings that have not been saved are skipped.

### Configure the export file path

Override `ConfigurationConfig::getExportFile()` in your project configuration to define the export file path. The command throws an exception if you do not provide this override.

**src/Pyz/Shared/Configuration/ConfigurationConfig.php**

```php
<?php

namespace Pyz\Shared\Configuration;

use Spryker\Shared\Configuration\ConfigurationConfig as SprykerConfigurationConfig;

class ConfigurationConfig extends SprykerConfigurationConfig
{
    /**
     * @return string
     */
    public function getExportFile(): string
    {
        return APPLICATION_ROOT_DIR . '/data/export/configuration-values.json';
    }
}
```

Ensure that the export directory is available in the deployment container:

**.gitignore**

```diff
 /data/*
 !/data/import/
+!/data/export/
```

{% info_block warningBox "Verification" %}

Save a value in **Back Office&nbsp;&rarr;&nbsp;Configuration**, run the command for that setting key, and verify that the file is created and contains the value.

{% endinfo_block %}

## configuration:restore

```bash
console configuration:restore <setting key> [<setting key> ...]
```

Reads the configuration export file from the configured path and saves its values to the database.

The command skips a setting if the schema no longer defines it or declares it as secret. The command reports both cases.

The command deletes the export file only if all values are restored successfully. If any value fails to restore, the command retains the file so that you can address the error and run the command again.

### Configure the file path

`ConfigurationConfig::getExportFile()` throws an exception until you redefine it at the project level. The command reads from this path and does not guess one.

**src/Pyz/Shared/Configuration/ConfigurationConfig.php**

```php
<?php

namespace Pyz\Shared\Configuration;

use Spryker\Shared\Configuration\ConfigurationConfig as SprykerConfigurationConfig;

class ConfigurationConfig extends SprykerConfigurationConfig
{
    /**
     * @return string
     */
    public function getExportFile(): string
    {
        return APPLICATION_ROOT_DIR . '/data/export/configuration-values.json';
    }
}
```

{% info_block warningBox "Verification" %}

Place a configuration value file at the configured path, run the command for a setting key held in it, and verify that the value appears in **Back Office&nbsp;&rarr;&nbsp;Configuration** and that the file is removed.

{% endinfo_block %}

## configuration:import-environment

```bash
console configuration:import-environment <variable name> [<variable name> ...]
```

Saves the value of each specified environment variable as a configuration value. Settings declared with `secret: true` in the schema are encrypted when saved.

Pass environment variable names to the command, not their values. The command reads each value from the environment at runtime. This prevents secret values from being included in the command arguments or deployment configuration. If an environment variable is not set, the command reports it and skips the setting.

### Name the environment variables

Name each environment variable using the following format. Include the scope in every variable name, including the `global` scope:

| Pattern | Description |
| --- | --- |
| `configuration:global:<setting key>` | Configuration value in the global scope |
| `configuration:<scope>:<identifier>:<setting key>` | Configuration value in a specific scope and identifier, such as a store |

For example, use the following environment variable name for a global Google Analytics measurement ID:

```text
configuration:global:integrations:google_analytics:tracking:measurement_id
```

{% info_block warningBox "Do not commit values" %}

Set the values in the environment configuration of your hosting provider, not in a deploy file that is committed to the repository.

{% endinfo_block %}

{% info_block warningBox "Verification" %}

Set a variable for one setting, run the command with that variable name, and verify that the value appears in **Back Office&nbsp;&rarr;&nbsp;Configuration**.

{% endinfo_block %}

## Using the commands together

These commands support deployments that drop database tables and remove configuration values saved by Back Office users.

Run `configuration:export` before the deployment drops the tables. After the database is rebuilt, run `configuration:sync` to regenerate the settings map, then run `configuration:import-environment` and `configuration:restore` to restore the required values.

**config/install/destructive.yml**

```yaml
sections:
    configuration-export:
        configuration-export:
            command: >-
                vendor/bin/console configuration:export
                integrations:google_analytics:tracking:measurement_id
                -vvv --no-ansi

    # ... sections that drop and rebuild the database ...

    configuration:
        configuration-sync:
            command: 'vendor/bin/console configuration:sync -vvv --no-ansi'

        configuration-import-environment:
            command: >-
                vendor/bin/console configuration:import-environment
                configuration:global:integrations:google_analytics:connection:service_account_credentials_json
                -vvv --no-ansi

        configuration-restore:
            command: >-
                vendor/bin/console configuration:restore
                integrations:google_analytics:tracking:measurement_id
                -vvv --no-ansi
```

Both `configuration:restore` and `configuration:import-environment` write configuration values. If both commands write the same setting, the command that runs last determines the final value.

Choose the order based on which source should take precedence:

| Command order | Result |
| --- | --- |
| Import environment, then restore | The exported value takes precedence over the environment variable value. |
| Restore, then import environment | The environment variable value takes precedence over the exported value. |

{% info_block warningBox "Shared filesystem" %}

All sections in a single `vendor/bin/install` run must have access to the same export file. If your deployment runs each section in a separate container, configure a shared volume so that `configuration:restore` can access the file created by `configuration:export`.

{% endinfo_block %}

{% info_block warningBox "Check command output" %}

These commands can exit successfully even when they report errors. Do not rely on the exit code alone to determine whether the configuration values were exported, restored, or imported successfully. Check the command output during deployment.

{% endinfo_block %}

## Troubleshooting

| Symptom | Cause | Solution |
| --- | --- | --- |
| `Nothing stored for key "..."` during export | No value is stored for the setting | This is expected on the first deployment if the setting has not been saved. `configuration:sync` generates the settings map but does not create configuration values. |
| `Could not import secret setting "...": TypeError` | The encryption key or initialization vector is missing or invalid | Configure `SPRYKER_CONFIGURATION_ENCRYPTION_KEY` and `SPRYKER_CONFIGURATION_ENCRYPTION_INIT_VECTOR` with the required values. The command suppresses detailed errors for secret settings, so the message might not identify the exact cause. |
| `ConfigurationConfig::getExportFile() has to be redefined` | The project-level path is missing | Redefine `getExportFile()` in `src/Pyz/Shared/Configuration/ConfigurationConfig.php`. |
| `The configuration schema holds no settings` | The settings map has not been generated or contains no settings | Run `configuration:sync` before `configuration:restore` and `configuration:import-environment`. |
| `No export at "...", nothing to restore.` | No file exists at the configured path | Verify that `getExportFile()` returns the path where the file was written, and that the file is readable by the current user. |
| `Skipping "...": the name does not resolve to a setting key` | The environment variable name does not match a known setting key or scope | Verify the variable name and use the required format: `configuration:global:<setting key>` or `configuration:<scope>:<identifier>:<setting key>`. |
