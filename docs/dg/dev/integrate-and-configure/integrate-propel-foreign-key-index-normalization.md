On MySQL and MariaDB, Propel automatically creates a support index named `<table>-fi_<column>` for every foreign key column that isn't already covered by the leftmost column of another index. The primary key counts as such an index, so for a table with a *composite* primary key—for example, a cross-reference table like `spy_acl_user_has_group` with the primary key `(fk_user, fk_acl_group)`—the name of the generated index depends on the order of the primary key columns.

When several modules define the same table, `propel:schema:copy` merges their schema files and sorts the columns alphabetically. This can change the primary key column order compared to the one declared in the module, and with it the index name Propel expects. As a result, `propel:diff` generates a migration like the following for a database that was created before the merge or before the second schema file was added:

```sql
DROP INDEX `spy_acl_user_has_group-fi_acl_group` ON `spy_acl_user_has_group`;
CREATE INDEX `spy_acl_user_has_group-fi_user` ON `spy_acl_user_has_group` (`fk_user`);
```

On MySQL, the `DROP INDEX` statement fails because the index is still required by the foreign key constraint, so the migration can't be applied and is generated again on every `propel:diff` run. Because Propel doesn't compare the primary key column order, the difference can't be resolved by a migration.

Foreign key index normalization solves this by declaring the support index explicitly for *every* single-column foreign key whose column is part of a composite primary key. The expected set of indexes then no longer depends on the column order, and `propel:diff` only generates additive `CREATE INDEX` statements for indexes that are actually missing.

## Prerequisites

Install the following modules:

| MODULE | VERSION |
| --- | --- |
| Propel | 3.51.0 or later |

## 1) Enable the normalization

Enable the normalization in `config/Shared/config_default.php`:

```php
<?php

use Spryker\Shared\Propel\PropelConstants;

// ...

$config[PropelConstants::PROPEL_FOREIGN_KEY_INDEX_NORMALIZATION_ENABLED] = true;
```

{% info_block infoBox %}

The setting is disabled by default in the `Propel` module and enabled in the Spryker demo shops. It only affects the schema files generated by `propel:schema:copy`; the source schema files of the modules aren't changed.

{% endinfo_block %}

## 2) Generate the schema and the migration

Regenerate the merged schema files and check the resulting migration:

```bash
console propel:schema:copy
console propel:diff
```

{% info_block warningBox "Verification" %}

The generated migration in `src/Orm/Propel/Migration_<engine>/` contains only `CREATE INDEX` statements and no `DROP INDEX` statements. Each `CREATE INDEX` adds a `<table>-fi_<column>` index to a table with a composite primary key, for example:

```sql
CREATE INDEX `spy_acl_user_has_group-fi_user` ON `spy_acl_user_has_group` (`fk_user`);
```

{% endinfo_block %}

## 3) Apply the migration

Apply the migration and make sure no further differences are reported:

```bash
console propel:migrate
console propel:diff
```

{% info_block warningBox "Verification" %}

The second `propel:diff` run reports `Same XML and database structures for all datasource - no diff to generate`.

{% endinfo_block %}

{% info_block infoBox "Large tables" %}

The migration is applied once per environment. Adding an index to a large table—for example, `spy_product_offer_store` or `spy_product_abstract_product_option_group`—can take time and lock the table on older MySQL versions. Review the generated migration and, if needed, apply the `CREATE INDEX` statements manually during a maintenance window before running `propel:migrate`.

{% endinfo_block %}
