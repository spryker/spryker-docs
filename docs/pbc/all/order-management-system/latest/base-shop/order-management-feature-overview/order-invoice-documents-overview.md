{% info_block infoBox "Liability" %}

Spryker does not generate, validate, or assume legal responsibility for invoices or credit notes. The seller remains the invoice issuer and is responsible for the document's tax and legal compliance, including its format under applicable national e-invoicing mandates.

Spryker's role is limited to forwarding the document links from the seller, making it available to the correct buyer/seller.

Spryker does not transmit documents to national e-invoicing or clearance networks such as Peppol, KSeF, or SdI. Transmission remains the responsibility of the seller or their e-invoicing provider.

The legacy [Order confirmation / invoice notification email feature](/docs/pbc/all/order-management-system/latest/base-shop/order-management-feature-overview/invoice-generation-overview.html) is non compliant with the latest EU e-invoicing requirements.

{% endinfo_block %}

The *Order invoice documents* feature stores an invoice document for an order and makes it available in two places:

- On the Storefront, in a **Documents** section of the order details page in the customer's order history.
- In the Back Office, in a **Documents** block of the order page.

The document is created when the invoice of an order is generated by the OMS event `invoice-generate`, the same event the [legacy invoice notification email](/docs/pbc/all/order-management-system/latest/base-shop/order-management-feature-overview/invoice-generation-overview.html) uses. The feature extends the `SalesInvoice` module; it does not replace the legacy email, and both run side by side.

## How it works

1. A Back Office user triggers the `invoice-generate` event on a confirmed order. The `SalesInvoice` module creates the invoice record with its sequential reference, for example `Invoice-12`, and sends the invoice email as before.
2. If order invoice file generation is enabled, the module runs a stack of *order invoice file generator plugins*. Every plugin returns one or more files for the invoice. The default plugin renders the project's invoice Twig template, the same template the email uses, into a stand-alone HTML document.
3. Every file is written to a private file system of your choice, for example an S3 bucket, and linked to the invoice in the database with its format, filename, MIME type, size, and a UUID. The document stays as generated; it is not re-rendered later.
4. When an order is loaded, its invoices and files are added to the order data. The Storefront section and the Back Office block list one row per invoice and one link per file.
5. A link opens the document through an authorized download route. The default HTML document opens in a new browser tab and contains a **Save as PDF** button that opens the browser's print dialog. Other formats, for example a PDF or an XML provided by a project plugin, are downloaded as files.

## Storefront

On the order details page, below the order totals, the **Documents** section lists every invoice of the order that has at least one file: the invoice reference, the issue date, the merchant names of the order, and one link per file. Orders without a generated document show the text *No documents*.

A document can be opened only by the order owner. In B2B shops, company users who are allowed to see the orders of their company or business unit can open the documents of those orders as well. Every other request, including a request for an unknown document, answers with a 404 page, so the URL does not reveal whether an order or a document exists.

## Back Office

The order page shows a **Documents** block with the columns **Reference No.**, **Date**, **Merchant**, and **Documents**. Back Office users with access to the order page can open the documents. Orders without a generated document show *No documents for this order*. For details, see [View order invoice documents](/docs/pbc/all/order-management-system/latest/base-shop/manage-in-the-back-office/orders/view-order-invoice-documents.html).

## Default document

The default document is an HTML file rendered from the project's invoice template. It is a demo document: it is not a structured e-invoice (EN 16931, XRechnung, ZUGFeRD), and it inherits the constraints of the [legacy invoice template](/docs/pbc/all/order-management-system/latest/base-shop/order-management-feature-overview/invoice-generation-overview.html#invoice-template), such as the handling of product options and mixed tax rates. The PDF is produced by the buyer's browser through the **Save as PDF** button; page breaks and margins depend on the browser.

Projects that must issue compliant documents replace the default plugin with their own generator, for example one that fetches the PDF and the XRechnung XML from an ERP or an e-invoicing provider. For details, see [Replace the default order invoice document](/docs/pbc/all/order-management-system/latest/base-shop/replace-the-default-order-invoice-document.html).

## Configuration

| CONFIGURATION | DEFAULT | DESCRIPTION |
|---|---|---|
| `SalesInvoiceConfig::isOrderInvoiceFileGenerationEnabled()` (Shared config) | `false` | Single switch for the file generation, the order data expansion, and both download routes. With the switch off, nothing is generated, the Storefront section and the Back Office block show their empty state, and the download routes answer 404. |
| `SalesInvoiceConstants::ORDER_INVOICE_FILE_SYSTEM_NAME` | `sales-invoice-files` | Name of the file system that stores the documents. The file system must be private; documents are served only through the authorized download routes. |
| `SalesInvoiceConfig::getOrderInvoiceTemplatePath()` (Zed config) | — | Invoice Twig template used by the email and the default document. |
| `SalesInvoiceConfig::getOrderInvoiceDocumentTemplatePath()` (Zed config) | `@SalesInvoice/Invoice/document.twig` | Wrapper template that adds the **Save as PDF** button to the invoice template. |

For installation steps, see [Install the Order Invoice Documents feature](/docs/pbc/all/order-management-system/latest/base-shop/install-and-upgrade/install-features/install-the-order-invoice-documents-feature.html).

## Current constraints

- One invoice per order: the invoice is generated once, and re-triggering the event only completes missing files of the existing invoice.
- Credit notes, delivery notes, and other document types are not supported.
- In marketplace shops, the document covers the whole order; there is no document per merchant.
- Documents are not exposed through the Storefront API or the Back Office API.
- The invoice email does not contain the document as an attachment.
